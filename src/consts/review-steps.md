1. **Learn the repo's rules.** Read whichever of these exist: `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, `CONVENTIONS.md`, `STYLE.md`, `.github/pull_request_template.md`, the lint and format configs, and the repo's review rules. Note the test command, the package manager, the changelog and docs rules. Nothing is reported from this step.
2. **Understand the PR.** Title, body, linked issue, commit messages. Write down in one line what the PR claims to do (`claim`). A diff that does something else, or more, is a finding.
3. **Correctness of the diff.** For each changed hunk: logic errors, wrong conditions, missing `await`, off-by-one, null and empty cases, error handling that swallows failures, races, resource leaks.
4. **What else it can break.** For each changed function, type, export, config key, CLI flag or schema: find its callers and users across the repo, including other packages in a monorepo. Look for a changed signature or behaviour that a caller didn't get updated for, a breaking change to a public API with no major bump or note, a migration that old data won't survive.
5. **The repo's standards.** Against the repo's rules: naming, file layout, the patterns the repo already uses. Code that rewrites a helper the repo already has is a finding (name the helper). Unneeded complexity, dead code, leftover debug output.
6. **Tests.** Is the changed behaviour covered? A bug fix with no test that would have caught it, or a test that can't fail, is a finding. Name the case that's missing.
7. **Docs and release notes.** A change users can see with no docs, README, changelog or changeset update, when the repo's rules ask for one.
8. **Security.** Secrets in the diff, injection (SQL, shell, HTML), unchecked input at a trust boundary, weakened auth or permissions, unsafe workflow changes (`pull_request_target`, untrusted input in `run:`).
9. **Verify.** Re-read every finding against the code once more and drop the ones that don't hold, are style preferences the repo doesn't state, or repeat a comment already on the PR. Then set the verdict: `blocking` (a bug, a break or a security issue), `needs-changes` (missing tests, docs or a standards issue), `looks-good` (nothing left).
